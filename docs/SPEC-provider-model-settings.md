# SPEC — Раздельные настройки подключения и модели

Дополняет [SPEC-primitive-setup.md](./SPEC-primitive-setup.md), [SPEC-byollm-connection-test.md](./SPEC-byollm-connection-test.md) и [SPEC-byollm-reliability.md](./SPEC-byollm-reliability.md). Заменяет только прежний UI одной формы; плоский OpenAI-compatible конфиг и единственный адаптер остаются без изменений.

## Проблема

Сейчас `SetupScreen` объединяет endpoint, token, ID модели, Thinking, проверку и сохранение в один линейный набор полей (`src/ui/SetupScreen.tsx:10-24, 47-131`). Это создаёт две проблемы:

- пользователь должен знать точный ID модели ещё до того, как приложение попробует обратиться к провайдеру;
- OpenAI-compatible API обычно может отдать каталог через `GET /models`, но приложение этот путь не использует; при неподдерживаемом каталоге нет явно предусмотренного ручного сценария.

Настройку нужно разбить на самостоятельные блоки: сначала подключение к провайдеру, затем выбор модели. Автоматический список — удобство, а не обязательное требование: ручной ввод ID должен оставаться доступен всегда.

## Цели

1. В `/setup` показать два понятных блока: «Подключение к провайдеру» и «Выбор модели».
2. Сохранять endpoint и token отдельно от выбранной модели, не меняя формат `preferences.json`.
3. После сохранения подключения по запросу пользователя получать OpenAI-compatible список моделей (`GET <endpoint>/models`).
4. При отсутствии этого API, пустом ответе или ошибке разбора дать ввести ID вручную; при auth/network/rate-limit ошибках честно показать причину, а не выдавать их за отсутствие поддержки.
5. Оставить финальную проверку Chat Completions, streaming и tool calling только после выбора модели.
6. Не логировать token, `extraHeaders` и тела HTTP-ответов.

## Не входит в scope

- Каталог или пресеты конкретных вендоров.
- Автоматический выбор «лучшей» модели и определение её tool/reasoning capabilities по имени.
- Кеширование каталога в `preferences.json` или запросы в фоне.
- Native SDK для не-OpenAI-compatible API.
- UI для `extraHeaders`: существующее поле продолжает загружаться и передаваться в запросы, но редактируется вручную в JSON.

## Дизайн

### 1. Экраны и навигация

`setup` становится обзором настроек, а не формой всех полей:

```text
Настройки LLM

▸ Подключение к провайдеру  настроено / не настроено
  Выбор модели              gpt-4o-mini / не выбрана

Enter — открыть · ESC — назад
```

Добавляются экраны `provider-connection` и `model-selection` в `Screen` (`src/state/app.ts:7-12`); `App` маршрутизирует их в новые компоненты.

- На первом запуске bootstrap по-прежнему открывает `setup`: `isConfigured` означает наличие endpoint, token **и** model (`src/persistence.ts:17-19`, `src/bootstrap.ts:14-15`). Фокус обзора — на подключении.
- Пока endpoint/token не сохранены, пункт выбора модели визуально недоступен. Enter показывает короткую русскую подсказку, не открывает экран.
- Из дочернего экрана ESC возвращает в обзор. Из обзора ESC возвращает на предыдущий экран только при полной конфигурации; иначе показывает нынешнее требование закончить настройку.
- `/setup` и пункт меню открывают обзор. Их пользовательские подписи меняются на «настроить подключение и модель».

### 2. Блок «Подключение к провайдеру»

Новый `ProviderConnectionScreen` содержит только:

- `Endpoint` — базовый OpenAI-compatible URL без `/chat/completions`;
- `Token` — замаскированное поле;
- действие «Загрузить список моделей»;
- действие «Сохранить подключение».

`extraHeaders` не показываются, но сохраняются при merge с существующими preferences.

Сохранение валидирует непустые trimmed endpoint/token и записывает частичный `Preferences`. Если endpoint **или token** изменились относительно сохранённых значений, оно удаляет `model` и устанавливает `thinking: false`: прежняя модель и режим reasoning могут не быть доступны новому аккаунту или endpoint. Если подключение не изменилось, выбранная модель и Thinking сохраняются. После успешной записи экран остаётся открытым и показывает, что следующий шаг — выбор модели; ESC возвращает к обзору.

«Загрузить список моделей» использует несохранённые значения формы, поэтому пользователь может сначала проверить другой endpoint/token и не испортить рабочую конфигурацию. Действие не записывает файл. Оно доступно и до сохранения, но только при заполненных endpoint/token.

Проверка из прежней формы не переносится в этот блок: без выбранной модели она не может доказать работоспособность Chat Completions и tool calling. Результат получения каталога — лишь проверка доступа к соответствующему API.

### 3. Получение каталога моделей

Добавляется `src/agent/models.ts` с transport-независимой функцией:

```ts
export interface ProviderConnectionConfig {
  endpoint: string;
  token: string;
  extraHeaders?: Record<string, string>;
}

export type ModelsResult =
  | { kind: "available"; models: string[] }
  | { kind: "unsupported" };

export function listModels(
  config: ProviderConnectionConfig,
  signal?: AbortSignal,
): Promise<ModelsResult>;
```

`ProviderConfig` в `src/agent/providers/index.ts` расширяет `ProviderConnectionConfig`, добавляя `model` и `thinking`; это убирает дублирование параметров подключения между discovery и игровым провайдером.

Поведение `listModels`:

1. Строит URL как `${endpoint.replace(/\/+$/, "")}/models`, чтобы `/v1` не потерялся при `new URL` и не появлялся двойной слэш.
2. Выполняет `GET` с `Authorization: Bearer <token>`, `extraHeaders` и `AbortSignal`. `Authorization` задаётся после пользовательских заголовков, поэтому их значение не может заменить основной token; остальные дополнительные заголовки, например `x-api-key`, сохраняются.
3. На успешный OpenAI-совместимый ответ `{ data: [{ id: string }, ...] }` оставляет непустые строковые ID, удаляет дубликаты и сортирует по `localeCompare`. Пустой валидный список — `available` с пустым массивом.
4. Для HTTP 404, 405 или 501, а также успешного тела не формата списка возвращает `unsupported`: UI объясняет, что каталог недоступен, и предлагает ручной ввод.
5. Для 401/403, 429, прочих 4xx, 5xx и network/abort выбрасывает `ProviderError` через существующий `toProviderError` (`src/agent/providers/errors.ts`). UI показывает безопасное локализованное сообщение, аналогичное текущему `providerErrorMessage`; токен и ответ сервера не выводятся.

Запрос запускается только по Enter на «Загрузить» или «Обновить» — без фоновой загрузки и без persistence/cache. Экран создаёт `AbortController`, отменяет запрос при ESC/unmount и блокирует повторный запуск, пока запрос активен. Таймаут использует `config.loop.providerTimeoutMs`, как существующая полная проверка в `src/agent/connection.ts:16-46`.

### 4. Блок «Выбор модели»

`ModelSelectionScreen` открывается только при сохранённых endpoint/token. В нём находятся:

- текущий endpoint (без token) и действие «Обновить список»;
- список из последнего полученного в памяти результата, если он доступен;
- строковый фильтр и ограниченное окно результатов, чтобы длинный каталог не заполнял терминал;
- «Ввести ID вручную» — всегда доступное поле, в том числе когда список успешно получен;
- Thinking ON/OFF;
- «Проверить выбранную модель» и «Сохранить модель».

Список не сохраняется между открытиями экрана: при каждом входе пользователь явно нажимает «Обновить список». Выбранный из списка ID помещается в тот же локальный текстовый input, что и ручное значение. Таким образом сохранение и проверка не зависят от способа выбора.

При `unsupported`, пустом списке или ошибке загрузки экран остаётся рабочим: показывает соответствующий статус и фокусирует/предлагает ручной ID. Ошибки auth, лимита и сети не запрещают ручной ввод, поскольку endpoint может ограничивать именно `/models`; однако текст не утверждает, что подключение проверено.

«Проверить выбранную модель» сохраняет текущую семантику `checkConnection` из `src/agent/connection.ts:52-54`: создаёт обычный провайдер, отправляет streaming-запрос с `bartender_action` и возвращает `ready` либо `tools-unavailable`. Она работает с локальным выбранным ID и текущими сохранёнными endpoint/token, ничего не записывает. Thinking участвует в запросе. Сохранение не требует успешной проверки, как и текущая форма, но показывает её результат до следующего изменения полей.

«Сохранить модель» требует непустой trimmed ID, объединяет его и Thinking с сохранёнными настройками, вызывает `setPrefs` и после успеха возвращает в `bar`. Ошибка записи оставляет экран открытым, как предписывает `SPEC-byollm-reliability.md`.

### 5. Persistence и состояние

Формат файла не меняется:

```json
{
  "endpoint": "https://api.example.com/v1",
  "token": "sk-…",
  "model": "example-model",
  "thinking": false,
  "extraHeaders": { "X-Optional": "value" }
}
```

В `persistence.ts` добавляется экспортируемый `hasProviderConnection(prefs)`, проверяющий endpoint+token. `isConfigured` остаётся проверкой endpoint+token+model, поэтому `bootstrap` и игровой loop не запускают бар с частично сохранённым подключением. Миграция легаси и атомарная запись с `0o600` не меняются.

В app-store не добавляются секреты, кеш списка моделей или состояние сетевого запроса: это локальный React state экранов. Единственный persisted/source-of-truth конфиг остаётся в `prefs`.

### 6. Доступность списка и терминальная навигация

Существующий `SelectList` отображает все элементы и не рассчитан на пустой или очень большой набор (`src/ui/SelectList.tsx:13-42`). Для модели нужен отдельный контролируемый список либо расширение `SelectList` с `maxVisible`:

- фильтр вводится без сетевых запросов;
- стрелки выбирают результат из отфильтрованного набора;
- вокруг активного результата рендерится окно из 8–10 строк и строка вида «12–21 из 347»;
- при нулевом результате не вызывается навигация по модулю ноль, вместо этого показывается «Ничего не найдено — введи ID вручную».

Все надписи и ошибки — на русском. Token, extra headers и исходные ошибки API в кадр не попадают.

## План реализации

1. Добавить `hasProviderConnection` и общий `ProviderConnectionConfig`; покрыть частичные preferences и сохранить неизменность `isConfigured`.
2. Реализовать и изолированно протестировать `listModels`: URL, заголовки, нормализация данных, unsupported-ответы, HTTP-классификация и abort.
3. Ввести новые screen types, обзор настройки и маршрутизацию; обновить `/setup`, меню и back-навигацию.
4. Реализовать экран подключения: валидация, discovery на draft-значениях, сохранение partial prefs, инвалидирование model/Thinking при смене подключения.
5. Реализовать экран выбора модели: ручной ввод, список с фильтром/окном, refresh, Thinking, существующая полная проверка и сохранение.
6. Обновить README и все UI-тесты; затем выполнить `npm run typecheck`, `npm test`, `npm run build`.

## Критерии готовности

- Пользователь может сохранить endpoint/token, затем выбрать ID из `/models` или ввести его вручную.
- Отсутствие `/models` не блокирует ручную конфигурацию; ошибки доступа и сети не маскируются под неподдержку.
- Модель, выбранная для прежнего подключения, не используется после фактической смены endpoint/token.
- Бар открывается только с endpoint, token и model; финальная проверка по-прежнему проверяет streaming/tool calling.
- Секреты не выводятся и не добавляются в persistence сверх существующих полей.
- `npm run typecheck`, `npm test` и `npm run build` проходят.

## Оценка и риски

**M.** Основной объём — TUI-навигация и тесты, transport `/models` небольшой.

- Некоторые gateway поддерживают Chat Completions, но намеренно запрещают `/models`; ручной ID и финальная проверка — обязательный fallback.
- Результат `/models` не содержит надёжного признака tool calling или reasoning, поэтому возможности не определяются автоматически.
- Большие каталоги требуют оконного отображения; нельзя рендерить полный список без ограничения.
- Смена token может очистить рабочую модель, но это безопаснее запуска с моделью, недоступной новому аккаунту.
